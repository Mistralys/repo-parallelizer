## Summary

Every repo-parallelizer workspace folder (`{projectsFolder}/{projectId}/{workspaceId}/`) currently presents itself to a human or an AI agent as an unlabelled pile of repository folders, with no statement of what the workspace is for or what each folder contains. This plan generates three index files into each workspace folder — `README.md` (human-facing), `AGENTS.md` (agent-facing, auto-loaded as the root instruction file when a coding agent is started in that folder), and a one-line `CLAUDE.md` pointer — rendered from data the tool already owns: project name and description, workspace description and notes, and the repository list. To make those files answer the question that actually matters ("which of these folders is relevant to my request?"), an optional `Description` field is added to the repository model, editable in the repository modal. Because a generated index is only worth having if it is never stale, the six scattered `generateWorkspaceFile()` call sites are consolidated behind a single `WorkspaceArtifactsOrchestrator` choke-point that regenerates every per-workspace artefact together. That choke-point is then called from the endpoints that actually mutate the data it renders — the three metadata `PUT`s and, critically, the six live lifecycle routes (workspace delete/rename, project delete/rename, project repository link/unlink) that today bypass the orchestration layer entirely and do no filesystem work at all.

## Architectural Context

The backend is a strict bottom-up layering — Storage → Models → Error Log → Git → Orchestration → Server → CLI (`docs/agents/project-manifest/tech-stack.md`). Per-workspace on-disk artefacts are produced today by one module, `src/orchestration/vscode-workspace.ts`, whose `generateWorkspaceFile()` / `removeWorkspaceFile()` / `getWorkspaceFilePath()` functions are called from three orchestrators (`workspace-orchestrator.ts` L220/L264/L359/L360, `project-orchestrator.ts` L129/L193/L194, `repository-orchestrator.ts` L67 via a private helper used at L206 and L259) and one route handler (`src/server/routes/workspaces.ts` L362). Each call site rebuilds the `repoPaths` array by hand.

**Most of those call sites are not reachable in production today.** This is the single most important fact shaping this plan, and it is easy to miss when reading the orchestration layer in isolation. `ProjectOrchestrator` and `RepositoryOrchestrator` are never imported or instantiated outside their own modules and their own tests — a repo-wide grep finds only two JSDoc prose mentions in `src/orchestration/orchestration.types.ts` (L46, L60). `WorkspaceOrchestrator` *is* instantiated once (`src/server/index.ts` L97–L103) and handed to `registerWorkspaceRoutes()`, but the only method any handler calls on it is `createWorkspace()` (`src/server/routes/workspaces.ts` L319, the `/setup` route); `deleteWorkspace()` and `renameWorkspace()` have no production caller.

The lifecycle operations a user can actually trigger over HTTP therefore run straight through the data layer and touch the filesystem not at all:

| Live route | Handler calls | Filesystem work today |
|---|---|---|
| `DELETE /api/projects/:id/workspaces/:wid` (`routes/workspaces.ts` L285–L300) | `workspaceManager.remove()` (L291) | none |
| `PUT /api/projects/:id/workspaces/:wid/rename` (`routes/workspaces.ts` L247–L280) | `workspaceManager.rename()` (L273) | none |
| `DELETE /api/projects/:id` (`routes/projects.ts` L227–L235) | `projectManager.remove()` | none |
| `PUT /api/projects/:id/rename` (`routes/projects.ts` L187–L221) | `projectManager.rename()` | none |
| `POST /api/projects/:id/repositories` (`routes/projects.ts` L245–L279) | `projectManager.addRepository()` | none |
| `DELETE /api/projects/:id/repositories/:repoId` (`routes/projects.ts` L283–L297) | `projectManager.removeRepository()` | none |

`src/models/workspace/workspace.manager.ts` L197–L275 confirms `remove()` / `rename()` are pure data-layer methods with no `fs` calls. The consequence for this plan is direct: migrating the orchestrator classes onto a choke-point improves the orchestration layer but changes nothing a user can reach. The artefact set stays consistent only if the choke-point is also called from the six live handlers above — which is what step 8 does.

`registerProjectRoutes(router, projectManager)` (`src/server/routes/projects.ts` L31–L34, wired at `src/server/index.ts` L134) receives neither an `ErrorLogManager` nor any orchestrator, unlike `registerRepositoryRoutes()` and `registerWorkspaceRoutes()`, which both already take an `ErrorLogManager`.

On-disk layout is `{projectsFolder}/{projectId}/{workspaceId}/{repoId}/`, with the `.code-workspace` file one level up in the project folder (`getWorkspaceFilePath()`, `src/orchestration/vscode-workspace.ts` L21–L35). Every filesystem mutation under `projectsFolder` is preceded by a `path.resolve(...).startsWith(resolvedProjectsFolder + path.sep)` guard. `generateWorkspaceFile()` establishes the repository's convention for generated files that must tolerate user content: it preserves every JSON key except `folders`.

Health is reported by the side-effect-free `checkWorkspaceHealth()` (`src/orchestration/workspace-health.ts` L62–L140), which returns typed issues carrying a `fixAction` string; `gui/public/js/views/workspace-detail.js` (L893+) maps `fixAction` to a fix button and renders the message with no button for any unrecognised value. Repository CRUD runs through the stateless `RepositoryManager` (`src/models/repository/repository.manager.ts`) and `src/server/routes/repositories.ts`, with the GUI editing repositories through the modal at `gui/public/js/components/repository-modal.js`. Every GUI consumer of repository data obtains its object exclusively through `normaliseRepo()` (`gui/public/js/utils/normalise.js` L24–L31), which maps a fixed key set (`id`, `name`, `url`, `credentialId`, `LastRefreshedAt`) and silently drops any other backend field — so a new backend field is invisible to all three views until that function maps it.

Validation limits are centralized: every `MAX_*` constant in the codebase lives in `src/config/config.constants.ts`, including the four per-entity string-length limits `MAX_CREDENTIAL_ID_LENGTH` / `MAX_CREDENTIAL_LABEL_LENGTH` / `MAX_CREDENTIAL_HOST_LENGTH` / `MAX_CREDENTIAL_TOKEN_LENGTH` (L88–L109). No `src/models/**/*.types.ts` file exports a `MAX_*` constant.

## Approach / Architecture

Four layers, bottom-up:

1. **Data (`src/models/repository/`).** `Repository` gains an optional `Description?: string`, following the `CredentialId` precedent — optional field, no `SCHEMA_VERSION` bump (`docs/agents/project-manifest/constraints.md` § Schema Version Policy). `RepositoryManager.add()` and `.update()` accept an optional `description`, trim it, enforce `MAX_REPOSITORY_DESCRIPTION_LENGTH`, and omit the key entirely when the trimmed value is empty.

2. **Rendering (`src/orchestration/workspace-index.ts`, new).** A stateless module in the same shape as `vscode-workspace.ts`: pure renderers (`renderWorkspaceReadme()`, `renderWorkspaceAgents()`, `renderClaudePointer()`) plus a writer (`writeWorkspaceIndexFiles()`) and a remover (`removeWorkspaceIndexFiles()`). Generated content is wrapped in `<!-- paralizer:generated:begin -->` / `<!-- paralizer:generated:end -->` fences; text outside the fence is preserved verbatim on regeneration, mirroring `generateWorkspaceFile()`'s key-preservation contract. A file that exists **without** a begin marker is treated as hand-authored and is never touched — the write is skipped and surfaced as a health issue rather than silently clobbering a user's file.

3. **Choke-point (`src/orchestration/workspace-artifacts.ts`, new).** A `WorkspaceArtifactsOrchestrator` (config + `ProjectManager` + `RepositoryManager`) becomes the single place that knows what a "per-workspace artefact set" is. It exposes `regenerateWorkspace()`, `regenerateProject()`, `regenerateForRepository()`, and `removeWorkspace()`, and internally calls both `generateWorkspaceFile()` and `writeWorkspaceIndexFiles()`. All ten existing generate/remove call sites are migrated onto it; the three orchestrators and the workspace/repository/project route registrars receive it by constructor/parameter injection, wired once in `src/server/index.ts` (L97–L137).

   **Wiring it into the live lifecycle routes is a separate, larger half of this work** (step 8), because — as the Architectural Context sets out — six of the lifecycle operations a user can trigger over HTTP bypass the orchestration layer entirely and do no filesystem work at all. Migrating the orchestrator classes (step 7) is what stops artefact knowledge existing in two places; calling the choke-point from the live handlers is what makes the artefact set actually consistent. The plan does both, and the scope of the second is deliberately bounded to **artefact reconciliation only**: the handlers gain `.code-workspace` and index-file regeneration/removal, and gain nothing else. They do not start deleting clone folders on workspace delete, and they do not start renaming on-disk folders on rename — those are the behaviour changes that wiring the full `WorkspaceOrchestrator`/`ProjectOrchestrator` methods would bring, they are product decisions rather than consequences of adding an index file, and they are listed in Out of Scope.

4. **Surfacing (routes, health, GUI).** Repository description is editable in the modal and displayed in the repositories list and detail views. `checkWorkspaceHealth()` gains index-file checks. The existing `POST /api/projects/:id/workspaces/:wid/regenerate-workspace-file` endpoint keeps its path (API compatibility) and now regenerates the full artefact set. Metadata edits (`PUT /api/repositories/:id`, `PUT /api/projects/:id`, `PUT /api/projects/:id/workspaces/:wid`) trigger regeneration so a description or note edit is reflected without a manual step.

**Generated file contents.** `README.md` and `AGENTS.md` share one rendered index body: project name + description, workspace ID + description + notes, a repository table (`Folder | Name | Description | Remote URL`, ordered by `project.Repositories`), a link to the workspace's GUI page built from `config.serverPort`, and a generation timestamp plus tool version. `AGENTS.md` additionally carries a short directives block: each subfolder is an independent git repository with its own instruction files that must be read before working in it; no cross-folder relative imports; live branch/status lives in the GUI, not here; content inside the fence is regenerated. `CLAUDE.md` is a single `@AGENTS.md` line — the exact pattern this repository already uses at its own root (`CLAUDE.md` → `@AGENTS.md`), which keeps the design independent of any particular agent's native `AGENTS.md` support.

**Volatile data is excluded by design.** No current branch, no dirty state, no ahead/behind counts. A generated file that reports live git state is a file that is wrong within the hour; the GUI owns live state and the index links to it.

## Rationale

- **Three files, one renderer.** `README.md` alone is not loaded into an agent's context; `AGENTS.md`/`CLAUDE.md` alone are ignored by humans browsing the folder. Both audiences are real, and rendering both from one context object makes divergence impossible.
- **Choke-point before artefact.** Adding a second artefact to six hand-written call sites guarantees that call site number seven forgets it. The choke-point is the only structure that keeps the index honest as the codebase grows, and it is cheapest to build now, while all six sites are already being touched.
- **Fence-based merge over full overwrite.** The user will want to add workspace-specific prose. Full overwrite destroys it; never overwriting makes the index stale. The fence gives both, and matches the existing `generateWorkspaceFile()` contract.
- **Never create the workspace folder.** The folder's existence is a load-bearing signal — `POST …/regenerate-workspace-file` returns 400 when it is absent ("Run setup first"), and health checks treat an uninitialised workspace as healthy. Writing an index file into a non-existent folder would fabricate an initialised-looking workspace. Index writes are therefore a no-op when the folder is absent, while `.code-workspace` generation keeps its current semantics unchanged.
- **Descriptions are the payload.** Without a per-repository description the table degrades to `paralizer | paralizer | https://…`, which does not answer "is this repo relevant to my request" — the exact problem motivating the feature.

## Pattern Alignment

- **Stateless module for filesystem generation** — `src/orchestration/workspace-index.ts` follows `src/orchestration/vscode-workspace.ts`: exported pure functions, explicit path arguments, no class state. Followed.
- **Orchestrator composes managers via constructor injection** — `WorkspaceArtifactsOrchestrator` mirrors `RepositoryOrchestrator` (`src/orchestration/repository-orchestrator.ts` L38–L43). Followed.

Followed, and extended with a realpath and a shape check per insights `f13a8d1a` / `d205d609`; the extension is an addition to the pattern, not a departure.
- **Generated files preserve user content** — `generateWorkspaceFile()` preserves all non-`folders` keys; the index writer preserves everything outside the fence. Followed.
- **Optional field, no `SCHEMA_VERSION` bump** — `docs/agents/project-manifest/constraints.md` § Schema Version Policy, `Repository.CredentialId` precedent. Followed.

Followed.
- **Centralized `MAX_*` limit constants** — `MAX_REPOSITORY_DESCRIPTION_LENGTH` is declared in `src/config/config.constants.ts` beside the four credential-length limits (L88–L109), not in `repository.types.ts`. Followed; the earlier draft of this plan placed it in the model's types file, which would have made it the codebase's first model-scoped limit constant for no reason the credential precedent does not already cover.
- **Route registrars receive an `ErrorLogManager` when they log side-effect failures** — `registerRepositoryRoutes()` and `registerWorkspaceRoutes()` already do; `registerProjectRoutes()` gains one in step 8 so the project routes can log a regeneration warning. Followed.
- **Route handler validates and trims at the boundary** — `src/server/routes/repositories.ts` L173–L212. Followed.

## Detailed Steps

1. **Add `Description` to the repository model.** In `src/models/repository/repository.types.ts`, add `Description?: string` to `Repository` with JSDoc. ## Assumptions

- The workspace folder is not itself a git repository, so the generated files need no `.gitignore` handling; they sit beside — never inside — the cloned repositories.
- Agents started in a workspace folder load the root `CLAUDE.md` / `AGENTS.md` of that folder, and load a nested repository's own instruction files when they read files in that subtree — the behaviour this repository already relies on via its own `CLAUDE.md` → `@AGENTS.md` pointer.
- `config.serverPort` is sufficient to build a usable local GUI link (`http://localhost:{serverPort}/#/…`); no hostname configuration is needed for single-developer local use, as stated in `docs/agents/project-manifest/tech-stack.md`.
- A 500-character description limit is generous for a one-or-two-line summary while keeping the markdown table readable.

## Constraints

- All relative imports carry the `.js` extension (Node16 ESM).
- Optional-field addition — `SCHEMA_VERSION` must **not** be bumped.
- Index writes must never create the workspace folder; `.code-workspace` generation semantics must not change.
- `checkWorkspaceHealth()` must remain side-effect free.
- Any work package adding or modifying exported types must include the type-audit acceptance criterion from `docs/agents/project-manifest/constraints.md`.
- Tests creating temp files must register a `process.on('exit')` cleanup handler.
- Static routes must be registered before same-segment-count `:id` wildcards (no new routes are added by this plan, but the ordering must not be disturbed).

## Out of Scope

- A project-level index file listing workspaces — repositories are isolated by design and the user starts sessions at the workspace level.
- Deriving repository descriptions from each clone's own `README.md` or from a remote host API (see Deferred Items).
- Any live git state (branch, dirty status, ahead/behind) in the generated files.
- A configuration flag to disable index generation — generation is unconditional.
- Showing repository descriptions in the workspace-detail repository table.
- Localisation of generated file content.
- **Wiring the full `WorkspaceOrchestrator` / `ProjectOrchestrator` / `RepositoryOrchestrator` lifecycle methods into the live routes.** Step 8 adds artefact reconciliation to those handlers and nothing else. Making `DELETE …/workspaces/:wid` delete the user's clone folders, making rename move the on-disk folder, or making `POST /api/projects/:id/repositories` clone into every workspace are real product changes to what the API does with user data; they would ride in unexamined under an index-file feature and carry a far larger regression surface. They are recorded here, with verified evidence in the research brief, so the next plan touching this area inherits a clear statement of the gap rather than rediscovering it.
- Reconciling the pre-existing metadata/filesystem divergence in the two rename routes (metadata is renamed; the on-disk folder keeps its old name). Step 8 stops the index amplifying it and lets the health check surface it; fixing it is separate work.

Integration-style orchestrator tests extend the existing `src/tests/*-orchestrator.test.ts` files to assert that each lifecycle operation now produces or removes the full artefact set. Route tests extend `src/server/__tests__/routes/` using the existing `mock-http.ts` helper. GUI behaviour is covered by jsdom `.test.mjs` tests beside the modules they exercise. Per insight `9c2b0bde-7de0-4093-8996-226d94d2fbc8`, freshness assertions sample a value that **must be present** after regeneration (e.g. an edited description appearing in the file), never the absence of a value.

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| **A user's hand-written workspace README is overwritten** | Files without the begin marker are never modified or deleted; the fence merge preserves everything outside it; both behaviours are covered by dedicated tests (AC-07, AC-08). |
| **The index goes stale and starts lying** | A single regeneration choke-point that every lifecycle path and every metadata-edit endpoint calls, plus a health check that reports a missing index and a GUI button to regenerate on demand. |
| **The choke-point is built but never reached from the operations users actually perform** | The highest-impact risk in this plan, and the reason step 8 exists: six live delete/rename/link handlers bypass the orchestration layer entirely and do no filesystem work today, so migrating the orchestrator classes alone would leave every index stale on delete and rename while orchestrator-level tests passed. Step 8 wires the choke-point into those handlers directly, and AC-12's test obligations are pinned to route-level tests driven through `mock-http.ts` — a class-level test is explicitly stated not to satisfy them. |
| **Artefact bookkeeping turns a working delete or rename into a 500** | Every artefact call added in step 8 is wrapped: a failure appends a `Severity: 'warning'` error-log entry and the handler returns the response it would have sent anyway. Asserted by the AC-20 contract-preservation tests, which drive each handler with a throwing orchestrator stub. |
| **Wiring the choke-point into live routes silently changes what those routes do to user data** | Step 8 is bounded to artefact reconciliation: no clone-folder deletion, no on-disk folder rename, no cloning. The full-orchestrator alternative is recorded in Considered Alternatives and Out of Scope with its reason, and AC-20 asserts that status codes, response bodies, and the `STABLE` rejection are unchanged. |
| **A new backend field never reaches the GUI** | `normaliseRepo()` drops unmapped fields with no error and no symptom beyond a blank column; step 3 leads with the `description` mapping and flags it as a precondition, and a new `normalise.test.mjs` covers it directly. |
| **Index writing fabricates an initialised-looking workspace folder** | Index writes are a strict no-op when the workspace folder is absent, with no `mkdir`; asserted by a dedicated test (AC-09). |
| **A regeneration failure breaks an ordinary repository or project edit** | Regeneration on metadata edits is wrapped; failures append a `Severity: 'warning'` error-log entry and the edit still returns success (AC-13). |
| **Migrating ten call sites regresses `.code-workspace` behaviour** | `generateWorkspaceFile()` itself is untouched; the choke-point preserves its current semantics verbatim, including writing for uninitialised workspaces, and the existing orchestrator tests are extended rather than replaced (AC-10, AC-12). |
| **User-supplied text breaks the generated markdown or injects content** | All table cells pass through `escapeMarkdownCell()`; notes render in a block section rather than a table cell; covered by AC-06. Per insight `7d13934f-9d72-4156-9616-15741f3e8f94`, structural safety is guaranteed — semantic usefulness of a description remains the author's responsibility. |
| **A symlinked workspace folder redirects writes outside `projectsFolder`** | Layered lexical, realpath, and shape guards run before any I/O, per insights `f13a8d1a-5b81-427b-a09b-e15a5b280adc` and `d205d609-44bd-4411-8b6d-94a19e4a9e2c`; covered by AC-09. |
| **Routing `DELETE /api/repositories/:id` through `deleteRepositoryGlobally()` changes deletion behaviour** | The orchestrator method is already implemented and covered by five existing tests in `src/tests/repository-orchestrator.test.ts`; the route change preserves its current status-code mapping and `204` response, and the new behaviour is what the GUI's confirmation dialog already promises (`gui/public/js/views/repositories.js` L135). |
| **New constructor parameters break existing test construction sites** | The orchestrator is injected as an explicit constructor argument wired once in `src/server/index.ts`; existing orchestrator tests are updated in the same work packages that change the constructors. |
| **AC-13's workspace-description regeneration trigger is unreachable from the GUI** | `workspace.description` could only be set once, at creation; step 15 gives it the same post-creation edit affordance `notes` already has, wired to the same `PUT /api/projects/:id/workspaces/:wid` regeneration path from step 9. Asserted by AC-21. |

## Recommended Workflow

- **Workflow:** ledger
- **Rationale:** The change is cross-cutting — data model, REST API, two new orchestration modules, a ten-site refactor, new artefact side effects on six live lifecycle routes, health reporting, and five GUI modules — with a filesystem write path and new delete-path side effects that warrant dedicated security-audit and review stages.
