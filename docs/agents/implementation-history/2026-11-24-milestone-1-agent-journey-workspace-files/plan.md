## Summary

Improve the generated workspace files (`README.md` / `AGENTS.md` / `CLAUDE.md`, the region between the `paralizer:generated` markers) so an AI agent entering a workspace gets accurate orientation, directly usable guidance and durable, owner-defined rules. The work is delivered in three feature phases (A to C), preceded by a preparation step that captures the golden oracle and followed by a finalisation step for documentation and release preparation:

- **Preparation (oracle capture):** golden baseline of the current README/AGENTS output, produced by a committed capture script.
- **Phase A (static text, no model change):** replace the unusable "use the GUI for git state" directive with read-only `git -C` guidance, add reading order and precedence, add the `.workspace/` "where things live" notes and the generated-file marker rule, give ready-to-run CLI listing commands, and ship a `paralizer regenerate` command so existing workspaces actually receive the new text.
- **Phase B (derived data):** a "Workspaces" sibling table (ID, relative + absolute folder, GUI URL, "this one" marker) derived from `project.Workspaces` and the fixed on-disk layout `projectsFolder/<projectId>/<workspaceId>`, kept fresh by an index-only, per-workspace-isolated project refresh.
- **Phase C (new stored data):** project-level and workspace-level user-defined agent directives (model, REST, CLI, GUI), one flat list of user rules appended to the single `## Agent Directives` section (fixed bullets, then project rules, then workspace rules), and an optional per-repository "Role / relations" text (stored per project).
- **Finalisation:** documentation, changelog and version.

Generation stays a pure function of the stored model: no filesystem existence checks are added to rendering. Every new field is optional and, when empty, leaves the rendered output of the preceding phase byte-identical. No `SchemaVersion` bump is needed (additive optional fields, same precedent as `ProjectData.CustomFiles`).

`paralizer status` (formerly an optional Phase D) is deferred, see Deferred Items.

Source feedback is from a developer agent that worked in `ai-insights/DEV`; reference output: `/Users/smordziol/Webserver/Workspaces/ai-insights/DEV/AGENTS.md`.

Optional context fields mean "section omitted when empty". `writeWorkspaceIndexFiles()` (L443) handles marker merging and write guards and is a no-op when the workspace folder does not exist. `GENERATED_BEGIN_MARKER` / `GENERATED_END_MARKER` are exported at L29/L35; `escapeMarkdownCell` at L164.
- **Context builder / choke-point:** `src/orchestration/workspace-artifacts.ts` (`WorkspaceArtifactsOrchestrator.regenerateWorkspace/regenerateProject/regenerateForRepository/removeWorkspace`). Repositories are a global entity (`src/models/repository/repository.types.ts`, `repositories.json`).
- **Utilities layer:** `src/utils/` (`path-guard.ts`, `paths.ts`, `slug.ts`, `version.ts`) is the lowest layer, already imported by the renderer (`workspace-index.ts` imports `../utils/path-guard.js`) and usable from models.
- **REST:** `src/server/routes/projects.ts` (custom-files endpoints are the template, each mutation followed by best-effort `regenerateProject`), `src/server/routes/workspaces.ts`. Wiring in `src/server/index.ts`.
- **Workspace lifecycle paths (REST vs orchestrator):** the GUI's workspace rename and delete go through the REST handlers in `src/server/routes/workspaces.ts`, which call the managers and the artefact choke-point directly: rename (`PUT /api/projects/:id/workspaces/:wid/rename`, L303) runs `workspaceManager.rename` (L332), then `regenerateWorkspace(new)` + `removeWorkspace(old)` in one try/catch logged by the router-local `logArtifactWarning` (L108, L343), with no `workspaceMeta` override because the record is already renamed; delete (`DELETE /api/projects/:id/workspaces/:wid`, L357) runs `workspaceManager.remove` (L366), then `removeWorkspace` (L375, logged at L377). `WorkspaceOrchestrator.renameWorkspace()` (L261, moves the folder on disk, uses the `workspaceMeta` override) and `deleteWorkspace()` (L220) have no non-test callers in `src/`. - **GUI:** `gui/public/js/api.js`, `views/project-detail.js` (tab array; `views/project-custom-files.js` is the tab-module template), `views/workspace-detail.js` (generic `buildTextFieldSection`), jsdom `*.test.mjs` tests.

- **Known inconsistency:** `src/server/index.ts` L110-116 builds the artefact orchestrator without `repositoryFileManager`, so GUI-triggered regeneration omits the "Repository Files" section that CLI-triggered regeneration renders.

## Approach / Architecture

1. **Golden baseline first.** A committed capture script renders the shared fixture contexts and writes compiled TypeScript fixture modules before the renderer is touched. The README baseline backs "README unchanged through Phases A and B"; the AGENTS baseline backs an explicit gate after the behaviour-neutral renderer reshape (step 4) and is then retired.
2. **Make the renderer extensible before extending it.** Turn `AGENT_DIRECTIVES_BLOCK` into `renderAgentDirectives(ctx)`; extract the context literal in `regenerateWorkspace()` into a private `buildIndexContext()`; put the generated-marker and single-line rules into one shared utility module (`src/utils/single-paragraph-text.ts`) used by the renderer's sanitiser and, later, by the directive and role validators; fix the GUI server wiring so every trigger produces the same context.
3. **Phase A text** lives in the fixed directive/CLI/Custom Files/Repository Files renderers, AGENTS.md only (README byte-identical through Phases A and B). Per-repo reading paths are rendered as static text from `ctx.repositories` ("if present" wording), never checked on disk. The precedence wording is scoped to the generated overview (workspace and repository facts), so rules listed under `## Agent Directives` are not subordinated by it.
4. **Phase B** adds `siblingWorkspaces?: WorkspaceIndexSiblingRow[]` to the context (built by the choke-point from `project.Workspaces`, STABLE first then alphabetical), rendered as a `## Workspaces` table in AGENTS.md only, and only when the project has at least two workspaces. Create/rename/delete of a workspace — at the REST handlers in `src/server/routes/workspaces.ts`, which are the GUI path, and additionally in the `WorkspaceOrchestrator` rename/delete methods — call a new `WorkspaceArtifactsOrchestrator.refreshProjectIndexes(projectId)`: index files only (no `.code-workspace`, custom-file or repository-info writes), each workspace in its own try/catch, failures returned to the caller.
5. **Phase C** adds `AgentDirective` and an explicit `DirectiveScope` (new `src/models/project/directive.ts`), stored as optional `ProjectData.Directives?` and `ProjectWorkspace.Directives?`, with CRUD on `ProjectManager` taking a required scope argument (one method set, two scopes; no implicit default). Context carries plain strings (`projectDirectives?`, `workspaceDirectives?`). Rendering: one flat list in the single `## Agent Directives` section: fixed bullets, then project-level user rules, then workspace-level user rules. There are no "Workspace Rules"/"Project Rules" headings and no per-workspace subheading; for the agent these are simply the workspace's rules. Storage and the GUI/CLI editors keep the two scopes, and the generated CLI hint names both listing commands with the real IDs. With no user rules the output is byte-identical to the preceding phase. Repository role text is stored per project (`ProjectData.RepositoryRoles?: Record<repoId, string>`) and rendered as a fifth Repositories-table column only when at least one non-empty value exists.
6. **Surfaces** mirror custom files: REST endpoints with best-effort regeneration (project-scope directive and role mutations use `refreshProjectIndexes`, workspace-scope directive mutations use `regenerateWorkspace`), CLI groups `directives` and `repo-roles` (dependency-injected, exit codes 0/1/2), GUI tab "Directives" on the project page, a directives section on the workspace page, and an inline role cell in the project's repository table.
7. **Rollout:** new `paralizer regenerate [project-id] [--workspace <ID>]` command (no mutation needed) lets owners refresh existing workspaces after upgrading. It runs the full artefact regeneration per workspace (`regenerateWorkspace`), each workspace isolated in its own try/catch, and reports one line per workspace; the GUI "Regenerate Files" button remains the per-workspace route.

## Rationale

- Agents cannot drive a browser GUI and the CLI has no status command, so the only actionable generic advice is read-only `git -C <repo> status -sb`; this is zero maintenance and always accurate.
- Reading order and precedence are the cheapest correction to the most common failure (treating the generated workspace file as authoritative). Static per-repo paths keep generation pure; "if present" wording covers repos without those files. The precedence statement is limited to the generated overview because, with the flat list (Q2), the owner's durable rules share the section with bullet 1; an unscoped "this file is orientation only" would read as downgrading them, and a repository's own `AGENTS.md` rarely speaks to cross-repository conventions.
- Sibling workspaces are already modelled (`project.Workspaces`); only hand-typed prose carries the relationship today, so deriving the table is cheap and cannot drift.
- A sibling change only affects AGENTS.md. `regenerateProject()` would repeat the repository-info sync workspaces x repositories times and abort at the first failing workspace, defeating "all other workspaces" (AC-09). The index-only, isolated `refreshProjectIndexes()` is smaller than any workaround and stays inside the choke-point.
- Persisted directives belong in the data model (not in hand-edited regions of the generated file) because the generated region is overwritten and owners need one edit point for all workspaces; they are modelled on custom files because that gives GUI/REST/CLI/regeneration semantics for free and proven validation/test patterns.
- An explicit scope argument on the directive CRUD turns a missing workspace ID (e.g. an undefined route parameter) into a validation error instead of a silent edit of project-wide rules.
- The marker rule is a safety property; keeping it (and the newline-collapse rule) in one shared utility used by the renderer and both validators prevents the three copies from drifting.
- Notes as the carrier was evaluated and rejected (see Considered Alternatives): it is workspace-scoped only, has no CLI, mixes human scratch notes with rules, and rendering it multi-line into a generated file adds Markdown-structure and marker-injection risk.
- The role text is project-relative ("consumed by ai-insights"), while `Repository` is global and its name/description sync into git via `.workspace/info.json`; storing it on the project avoids cross-project leakage and avoids touching the sync payload and its hash.
- Reshaping `AGENT_DIRECTIVES_BLOCK` and extracting `buildIndexContext()` is paid for by this plan: three new optional context fields and the user-rule lists would otherwise be bolted onto a constant and a 20-line inline literal.
- The committed capture script (rather than a throw-away scratchpad script) makes both golden captures reproducible and auditable, and lets future intentional text changes re-capture the post-B golden instead of hand-editing fixture strings. The post-B golden is captured from the code under test, so it is a regression snapshot, not a correctness oracle: correctness of the new text is asserted by the targeted tests T-03 to T-07 and T-13 to T-18.

## Forward Compatibility with Milestone 2

Milestone 2 relocates project persistence into shareable stores. To keep that move cheap, all new data in this milestone obeys:

1. New fields (`Directives`, `RepositoryRoles`, workspace `Directives`) live inside `ProjectData` / `ProjectWorkspace`, never in a separate file or store.
2. They are read and written only through `ProjectManager`; no module (renderer, choke-point, CLI, route, GUI) touches project files directly.
3. They are optional, with no `SCHEMA_VERSION` bump.
4. Rendering must not depend on where the project is persisted: `buildIndexContext()` consumes the `ProjectData` returned by `ProjectManager` and nothing else (no path assumptions beyond `projectsFolder/<projectId>/<workspaceId>` for workspace folders).

## Pattern Alignment

- **Follows:** optional-field-means-section-omitted (`customFiles?`, `repositoryFiles?` in `src/orchestration/workspace-index.ts`); one `render*Section()` per section returning `''` when empty; context resolved by the choke-point only (`src/orchestration/workspace-artifacts.ts`); "one orchestrator entry point per trigger" (`regenerateWorkspace`, `regenerateProject`, `regenerateForRepository`, now `refreshProjectIndexes`); optional additive model fields without `SchemaVersion` bump (`ProjectData.CustomFiles` in `src/models/project/project.types.ts`); validation module per entity with exported limits (`src/models/project/custom-file.ts`) backed by shared scope-neutral helpers (`src/models/file-definition.ts`); UUID ids + `DateModified` CRUD on `ProjectManager`; REST handler shape with best-effort regeneration (`src/server/routes/projects.ts` L420-500); route-level artefact calls after workspace rename/delete, each in a try/catch logged via the router-local `logArtifactWarning` (`src/server/routes/workspaces.ts` L108, L339-344, L374-378) — the sibling refresh sits beside them; dependency-injected CLI group with `*_HELP`, `createDefault*Deps`, `Pick<WorkspaceArtifactsOrchestrator, ...>` deps, exit codes 0/1/2 (`src/cli/custom-files.ts`); tab-per-module GUI (`gui/public/js/views/project-custom-files.js`); tests compile into `dist/` so fixtures are `.ts` modules.
- **Departs (justified):**
  - Manager directive methods take a required `DirectiveScope` argument instead of the custom-file one-scope shape — directives exist at two scopes with identical rules, and the scope must never default silently.
  - The renderer's `AGENT_DIRECTIVES_BLOCK` constant becomes a function — it must now accept per-repo paths and user directives.
  - `file-command-helpers.resolveFileReference` is generalised (path matching optional) rather than copied for directives.
  - Roles are keyed by repository ID inside `ProjectData`, a map rather than the array-of-entities used by custom files — the value is a single string per repository with no identity of its own.
  - The marker/single-line helper lives in `src/utils/` rather than next to `GENERATED_*_MARKER` in `workspace-index.ts` — models (validators) must not import from the orchestration layer. A test pins that both exported marker constants contain the shared token.
  - A committed non-test script under `src/tests/fixtures/` — no `scripts/` folder exists; placing it under `src/` lets `tsc` compile it next to the fixtures it writes, and the test glob does not pick it up.

## Detailed Steps

### Preparation — Oracle capture

1. **Capture the baseline golden output (no dependencies; run before any other step).**
   - New `src/tests/fixtures/workspace-index-contexts.ts`: exports three `WorkspaceIndexContext` fixtures built independently of the renderer's current behaviour: (a) minimal, two repos, no custom/repository files, notes with one line; (b) custom files + repository files present, workspace with project and workspace description; (c) hostile strings (pipes, newlines, backticks) in names/descriptions/notes. Also exports a helper that derives a two-workspace variant of each context (adds `siblingWorkspaces` rows) once that field exists (step 9 extends this module; at step 1 only the three base contexts exist).
   - New committed capture script `src/tests/fixtures/capture-golden.ts` (not a test; outside the `dist/tests/*.test.js` glob): imports the fixture contexts and `renderWorkspaceReadme`/`renderWorkspaceAgents` and, for a target (`baseline` at this step, `postB` added in step 12), writes the fixture module of string constants. Paths are resolved from the package root. A `--check` flag compares the current rendering against the committed module and exits non-zero on any difference (printing the first differing line). ## Assumptions

- Workspaces of a project are always laid out as siblings under `projectsFolder/<projectId>/` (verified in code and on disk).
- Additive optional fields on `ProjectData`/`ProjectWorkspace` need no `SCHEMA_VERSION` bump (policy in `src/storage/storage.types.ts`; precedent `CustomFiles`).
- An older tool version reading newer data ignores the new fields and drops them on its next write (downgrade loses directives/roles); acceptable and documented.
- The next release is a minor version, `1.8.0` (`package.json` is 1.7.0 and 1.7.0 is the newest CHANGELOG entry); one changelog entry covers all phases unless the owner releases phases separately.
- `GET /api/projects/:id` returns the full `ProjectData` (verified, `projects.ts` L146-154).

## Constraints

- Generation remains a pure function of the stored model; no filesystem checks while rendering.
- Output stability: README.md is byte-identical through Phases A and B (T-01, T-02); with all Phase C fields empty/absent, README and AGENTS output equals the post-B golden (T-27).
- No relative imports without `.js`; every new test with temp files registers `process.on('exit')` cleanup (via `createTempDirTracker`).
- Callers must go through `WorkspaceArtifactsOrchestrator`; never import the index writers elsewhere (chokepoint guard test). `refreshProjectIndexes` lives inside the choke-point.
- Directives and roles are user text embedded in a generated file: must never contain generated-marker strings and must render as single-line list text; the rule is defined once in `src/utils/single-paragraph-text.ts`.

## Out of Scope

- A default built-in "cross-repo change convention" directive (separate commits per repository, release dependencies first). It is project-opinionated and is only documented as an example of a project directive owners can add (documented in README and the GUI help text: `paralizer directives add <project-id> --text "Commit per repository; release dependency repositories first, then consumers."`).
- A "last regenerated" line (the `_Generated by ..._` footer exists).
- A structured dependency graph between repositories.
- Reordering directives, directive templates, import/export of directives.
- Auto-regeneration at startup or on version change; health-check staleness detection.
- Changing `regenerateProject()`'s existing semantics.
- Publishing/tagging/releasing the new version.

Output-stability oracles: the README baseline (step 1; asserted by T-01/T-02), the AGENTS baseline (step 1; asserted once by the step-4 `--check` gate, then retired in step 5), and the post-B golden (step 12; a reviewed regression snapshot asserted by T-27). Both goldens are produced by the committed capture script, so intentional future text changes re-capture rather than hand-edit. Correctness of new text is asserted by targeted tests, not by the snapshots. Regression: all existing tests must pass; only the assertions about the old directive text are updated.

| Risk | Mitigation |
|------|------------|
| **User text corrupts the generated region (marker injection) or the table** | Shared marker neutralisation in `src/utils/single-paragraph-text.ts` (step 4), validation rejects marker strings through the same module (steps 13-14), single-paragraph text, tests T-09/T-19/T-26/T-45. |
| **Output drift for existing workspaces when new fields are empty** | Golden baseline, step-4 gate and post-B golden (steps 1, 4, 12), tests T-01/T-02/T-27; all new fields optional. |
| **Post-B golden enshrines a wrong rendering** | It is captured from reviewed output and treated as a regression snapshot; correctness is asserted independently by T-03 to T-07 and T-13 to T-18. |
| **GUI vs CLI regeneration produce different files** | Step 2 wiring fix, `buildIndexContext()` shared path, T-10/T-11. |
| **Sibling table stale after workspace create/rename/delete** | Step 10 `refreshProjectIndexes` with per-workspace isolation, so one failing workspace does not leave the others stale. Triggers sit in the REST handlers of `src/server/routes/workspaces.ts` (the GUI path, which does not go through `WorkspaceOrchestrator`), in their own try/catch after the existing artefact block, and also in the orchestrator rename/delete methods (orchestrator rename ordering preserved: regenerate with `workspaceMeta`, then refresh after the record rename). Residual: refresh is best-effort (failures logged). T-16/T-17/T-44. |
| **A future lifecycle entry point bypasses both trigger sites** | The orchestrator docblocks and `data-flows.md` name both trigger sites; T-17 pins the route path and T-16 the orchestrator path. |
| **Existing workspaces never receive the new text** | `paralizer regenerate` (step 7) with per-workspace isolation and reporting, and Human Action 3; footer version shows staleness. |
| **Absolute paths in the sibling table are machine-specific** | The file already embeds `toolRoot`; files are generated per machine and not committed; documented. |
| **`repo-files list` needs a repository ID, not project ID (deviation from the request wording)** | Render with the first repository's real ID and explicit "substitute another folder" wording; decided (Q3). |
| **Milestone 2 relocates project data and breaks Milestone 1 assumptions** | Forward-compatibility rules (ProjectData-only fields, ProjectManager-only access, optional, persistence-independent rendering). |
| **Project and workspace rules indistinguishable in the generated file** | Intentional (Q2): the agent treats them as the workspace's rules; the scope is visible in the GUI/CLI editors, and the CLI hint names both `paralizer directives list` commands (project and `--workspace`) with the real IDs. |
