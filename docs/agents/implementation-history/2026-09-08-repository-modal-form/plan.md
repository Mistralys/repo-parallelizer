## Summary

Convert the Repositories screen's "Add Repository" inline form and per-row inline Name editing into a single, reusable modal component (`repository-modal.js`) that supports both **create** and **edit** modes. The credential field — today only settable from the separate Repository Detail page — becomes part of this shared form from the start, available when creating a new repository and when editing an existing one. Following the Confirm-phase decision, the edit mode also makes the repository **URL** editable (previously edit only allowed the Name); the repository **ID** remains read-only/display-only in edit mode, since renaming it would require cascading updates across every project's repository references and every already-cloned folder on disk — a materially larger, separately-scoped capability (see Out of Scope).

## Architectural Context

The GUI is a vanilla-JS SPA with no build step and no framework (`gui/public/js/`). The only existing modal is `components/confirm-dialog.js`'s `showConfirm()`, a Promise-based dialog built fresh on every invocation and appended to `document.body`, using CSS classes already defined in `styles.css` (`.modal-overlay`, `.modal`, `.modal-title`, `.modal-body`, `.modal-actions`). Forms throughout the app are assembled via `components/form-helpers.js` (`createFormField()`, `validateRequired()`). The Repositories view (`views/repositories.js`) currently builds its own bespoke inline "Add Repository" form and a per-row inline Name-edit toggle, both of which bypass the shared modal pattern entirely.

On the backend, `src/server/routes/repositories.ts` registers all `/api/repositories*` routes against `RepositoryManager` (`src/models/repository/repository.manager.ts`), a stateless, disk-backed manager. Credential matching for an existing repository is already exposed via `GET /api/repositories/:id/credential-options`, which filters `AppConfig.gitCredentials` by hostname (`extractHost()` from `git/git-credentials.ts`) and masks tokens. `PUT /api/repositories/:id/credential` assigns/clears `Repository.CredentialId` with host-coherence validation and audit logging.

## Approach / Architecture

1. **New shared modal-shell primitive** (`components/modal-shell.js`) exporting `createModalShell({ titleText, ariaLabelledbyId, ariaDescribedbyId, className, onCancel })`, extracted from `confirm-dialog.js`'s hand-rolled overlay/modal/ARIA/Escape/backdrop-cancel DOM construction. It builds the `.modal-overlay` > `.modal` > `.modal-title` structure, wires Escape and backdrop-click to invoke the caller's `onCancel`, and adds three capabilities neither `confirm-dialog.js` nor the original plan's `repository-modal.js` design had: a focus trap (Tab/Shift+Tab cycles within the modal's focusable elements), focus restoration (captures `document.activeElement` before mount and restores it on `close()`), and a `setBusy(bool)` gate that makes Escape and backdrop-click inert while a caller-flagged operation is in flight. `confirm-dialog.js` is refactored to build on this shell — its public `showConfirm()` contract is unchanged. `repository-modal.js` (below) builds on the same shell from the start instead of hand-rolling its own copy.
2. **New shared modal component** (`components/repository-modal.js`) exporting `showRepositoryModal({ mode, repo? }): Promise<Repository>`, built on `modal-shell.js`, following the same Promise-resolve/reject-on-cancel contract as `showConfirm()`, but additionally owning its own async submit (API calls) and error display — mirroring the existing `buildAddRepoSection`'s "stay open, toast the error, let the user retry" behavior, now shared between create and edit. It calls `shell.setBusy(true)` for the duration of any in-flight create/update/credential call, so Submit, Cancel, Escape, and backdrop-click are all inert until the call settles, and re-enables everything on failure.
3. **New backend capability**: a URL-keyed credential-matching endpoint (`GET /api/repositories/credential-options?url=`) so the modal can populate the credential dropdown **before** a repository exists (create mode) and whenever the URL changes (edit mode), without depending on a stored repository record. This reuses the exact filter/mask/`autoSelected` logic already implemented for the by-ID endpoint (extracted into a small shared private helper to avoid duplicating it).
4. **Extended repository update**: `PUT /api/repositories/:id` gains an optional `url` field (duplicate-URL and embedded-credential-stripping validation mirrored from `add()`), plus a defense-in-depth step that clears an existing `CredentialId` when a URL edit makes it host-incoherent (reusing the existing `updateCredential()` method and audit-log shape).
5. **View simplification**: `views/repositories.js` drops its bespoke inline form and inline Name-edit machinery in favor of calling `showRepositoryModal()` for both the "+ Add Repository" action and each row's "Edit" action.

## Rationale

- **The overlay/modal/ARIA/Escape/backdrop-cancel DOM-building itself is extracted into `modal-shell.js`, one level below the modal-vs-confirm-dialog split**, rather than reversing that split. The original plan's separation between a synchronous `confirm-dialog.js` and an async, multi-field `repository-modal.js` remains: the shell only owns DOM/ARIA/focus/busy-gating plumbing, never submit logic, error display, or field construction. This is prompted directly by this plan adding `repository-modal.js` as a second consumer of that plumbing — the two prior implementation-history syntheses (`docs/agents/implementation-history/2026-04-03-phase6-gui-frontend/synthesis.md`, `-rework-1/plan.md`) explicitly accepted "no focus trap in confirm-dialog" and "hard-coded ARIA IDs" as low-priority risks specifically because the dialog had exactly one shape and one caller pattern at the time; a second, more complex consumer removes the "used exactly once, low blast radius" grounds for continuing to defer the focus-trap gap (this plan does not address the hard-coded-ARIA-IDs item — see Out of Scope).
- **Focus trap and focus restoration are implemented once, inside the shared shell**, rather than separately inside `confirm-dialog.js` and `repository-modal.js`, so both dialogs get identical accessibility behavior by construction and neither implementation can silently drift from the other — the same reasoning the plan already applies to the credential-matching endpoint being one code path serving both modal modes.
- **The submit-in-flight guard is a generic `setBusy()` gate on the shell**, not a `repository-modal.js`-only mechanism, because the shell already owns the Escape/backdrop-cancel wiring that the guard must suppress; adding a second, parallel busy-flag check inside `repository-modal.js` itself would duplicate that wiring's cancel-path instead of gating the one implementation that already exists.
- The modal is a new, dedicated component (not an extension of `confirm-dialog.js`) because it owns an async multi-field submit with inline retry-on-error, a fundamentally different responsibility than a synchronous yes/no confirmation. Reusing `showConfirm()`'s DOM-building conventions (overlay/modal/title/actions classes, ARIA attributes, Escape/backdrop-cancel) — now via the shared shell rather than by hand — keeps it visually and behaviorally consistent without forcing an ill-fitting shared implementation of the parts that do differ (submit, field construction, error display).
- A single component serving both create and edit (rather than two separate modals) is chosen because the two modes share four of four fields, differing only in which fields are disabled and which initial values are pre-filled — matching the codebase's general preference for one parameterized implementation over near-duplicate variants (e.g. `createFormField()` itself is one function serving many field types).
- The credential dropdown is sourced from a **new URL-keyed** endpoint rather than reusing the existing by-ID endpoint for edit mode, so that **one** code path serves both modes uniformly: the modal always matches against "whatever URL is currently in the form," which is empty-then-typed in create mode and pre-filled-then-editable in edit mode. This also means an in-edit URL change immediately and correctly refreshes the available credential options, which a by-ID-only approach could not do before the edit is saved.
- The backend auto-clears a `CredentialId` that a URL edit has made host-incoherent as a defense-in-depth data-integrity invariant enforced at the API boundary that owns the relationship — not merely relied upon via the GUI's own dropdown-refresh behavior, which independently produces the same end state in the normal flow (see Considered Alternatives).
- Repository ID stays read-only in edit mode (Confirm-phase decision) because it is both the storage key referenced from every project's `Repositories: string[]` array *and* the on-disk clone-folder slug (`{projectsFolder}/{projectId}/{workspaceId}/{repoId}`, confirmed in `branch-orchestrator.ts`, `repository-orchestrator.ts`, `workspace-orchestrator.ts`, `pollingManager.ts`, `workspaces.ts`). A safe rename would require renaming already-cloned folders across every project/workspace, rewriting every referencing project record, and regenerating `.code-workspace` files — comparable to (or larger than) the existing dedicated project/workspace rename endpoints, but with a much larger fan-out. This is deliberately deferred to its own future plan rather than folded into a UI-conversion task.

| Modal scope | One component (`repository-modal.js`) parameterized by `mode` | Two separate components (`add-repository-modal.js` / `edit-repository-modal.js`) | Two components would duplicate the field-building, credential-matching, and submit-retry logic almost entirely; a single parameterized component matches the existing one-function-many-configurations style of `createFormField()` and keeps the credential-matching behavior identical between modes by construction rather than by discipline. |
| Credential-matching source for the modal | New `GET /api/repositories/credential-options?url=` endpoint, used in both modes | Reuse the existing by-ID `GET /:id/credential-options` for edit mode only, and skip credential matching entirely in create mode until after the repository is created | The by-ID-only approach cannot match credentials before a repository exists (no ID yet), so "credential field available from the start" (an explicit requirement) would be impossible for create mode without it. It would also leave edit-mode credential options stale immediately after a URL change, until a save round-trip. |
| Host-incoherence handling on URL edit | Backend auto-clears the stale `CredentialId` (defense-in-depth), independently of the GUI's own dropdown refresh | Reject the URL edit outright when it would strand an assigned credential | Rejecting the edit forces the user to manually clear the credential first, an extra required step for what is normally an unremarkable edit; auto-clearing preserves the existing "assign explicitly, absence is a valid state" model already established for credentials and never silently uses a token for the wrong host. |

| Repository URL in edit mode | Editable, with a stated GUI caveat that already-cloned copies keep their old git remote | Read-only (matches today's behavior exactly) | Confirmed with the user during the Confirm phase: URL editing is materially more contained than ID rename (one manager method, one duplicate-URL check, no filesystem fan-out) and was explicitly requested; the stale-local-remote limitation is documented rather than silently ignored, and full remote re-pointing of existing clones is out of scope for this plan. |

A shell that owns only DOM/ARIA/focus/busy plumbing keeps that separation intact while eliminating the duplication. |

## Pattern Alignment

- **Introduces** a new shared low-level primitive, `components/modal-shell.js`, one layer below `confirm-dialog.js`'s and `repository-modal.js`'s existing Promise-based-dialog pattern — both build on it for DOM/ARIA/Escape/backdrop-cancel/focus-trap/focus-restoration, while retaining their own distinct submit/resolve semantics. This is a new pattern in the codebase (no prior shared-primitive-under-two-components precedent existed for the GUI's modal family), justified by exactly two named consumers as of this plan (see Structural Improvements) and the accessibility gaps both consumers otherwise share.
- **Follows** `components/confirm-dialog.js`'s modal-DOM/ARIA/cancel-semantics pattern (`.modal-overlay` > `.modal` > `.modal-title`/`.modal-actions`, Escape key, backdrop click, fresh DOM per invocation, Promise resolve/reject contract) — now realized via the shared shell rather than duplicated by hand a second time.
- **Follows** `components/form-helpers.js` for all field construction (`createFormField()`) and required-field validation (`validateRequired()`) — no hand-rolled form markup.
- **Follows** `views/settings.js`'s "read-only field inside an otherwise-editable form" pattern (Host is read-only in the credentials table's inline edit) for the repository ID field in edit mode.
- **Follows** `views/workspace-detail.js`'s `buildNotesSection()` closure-scoped debounce-timer pattern for the URL-change → credential re-match trigger.
- **Follows** the existing `PUT /api/repositories/:id/credential` route's host-coherence-guard and audit-log-entry shape for the new auto-clear-on-URL-change step — no new audit event type is introduced; it reuses `Operation: 'clear-credential'`.
- **Departs from** `views/repository-detail.js`'s `buildCredentialSection()` credential-source (`GET /:id/credential-options`): the modal uses the new URL-keyed endpoint instead, justified above (Considered Alternatives) by the need to match credentials before a repository exists and to react live to in-modal URL edits.

## Detailed Steps

### Backend

1. **Extend `RepositoryManager.update()`** (`src/models/repository/repository.manager.ts`): change the signature to `update(id: string, params: { name: string; url?: string }): Repository`. When `params.url` is provided: trim it; strip embedded credentials via `hasEmbeddedCredentials()`/`stripEmbeddedCredentials()` exactly as `add()` does; reject with a plain `Error` (mirroring `add()`'s duplicate-URL message style) if another repository (`r.Id !== id`) already has the cleaned URL; store the cleaned URL. When embedded credentials were stripped, return the updated repository spread with the transient `credentialsStripped: true` flag (matching `add()`'s existing contract), otherwise return the plain updated `Repository`. Preserve all existing behavior when `params.url` is omitted (name-only update, unchanged).
2. **Extend `PUT /api/repositories/:id`** (`src/server/routes/repositories.ts`): read an optional `url` field from the body alongside the existing required `name`; if present, it must be a non-empty string (400 otherwise, matching the existing `name` validation style). Call the extended `repoManager.update(id, { name, url })`. Catch thrown `Error`s from the duplicate-URL/manager validation path and respond `400` with the error message (mirroring the `POST /api/repositories` handler's existing error-surfacing convention); keep the existing `NotFoundError → 404` and other-error `→ 500` handling.
3. **Add the host-incoherence auto-clear step** in the same `PUT /api/repositories/:id` handler: after a successful update where `url` was provided and the repository had an existing `CredentialId` *before* the update, look up the matching entry in `appConfig.gitCredentials`; compute `extractHost()` of the *new* URL; if the credential's `host` does not match and the new host is not `null` (SSH), call `repoManager.updateCredential(id, null)`, append an audit-log entry (`Severity: 'audit'`, `Source: 'credential-audit'`, `Operation: 'clear-credential'`, `Context: { RepositoryId: id }`, a message noting the automatic clear was due to a URL/host change), and return the credential-cleared repository as the response body instead of the pre-clear one.
4. **Add `GET /api/repositories/credential-options`** (new route, same file): parse the `url` query parameter (reusing the `URLSearchParams`-on-split-query idiom already used in `error-log.ts`); respond `400` when `url` is missing or empty. Extract a private helper `buildCredentialOptionsResponse(host: string | null, credentials: GitCredentialEntry[]): { credentials: GitCredentialEntry[]; autoSelected?: string }` containing the filter/mask/`autoSelected` logic currently inlined in the by-ID handler; call it with `extractHost(url)` and `appConfig.gitCredentials`. Refactor the existing `GET /:id/credential-options` handler to call the same helper with `extractHost(repo.Url)`, so the two handlers share one implementation. Register the new route in the same `registerRepositoryRoutes()` function (registration order relative to the by-ID route does not matter — different path-segment counts, verified against `extractParams()`).
5. **Update the route registration docblock** at the top of `repositories.ts` (the `| Method | Path | Success | Failure |` table) to add the new endpoint and note the extended `PUT /:id` contract.

### Backend Tests

6. **`src/tests/repository.manager.test.ts`**: add tests for `update()` with a `url` param — successful update changes `Url`; duplicate-URL against another repository throws; embedded credentials in the provided URL are stripped and `credentialsStripped: true` is returned; a `url`-omitted call behaves exactly as before (regression guard).
7. **`src/server/__tests__/routes/repositories.test.ts`**: add tests for the extended `PUT /:id` — accepts `{name, url}` and persists both; rejects duplicate URL with 400; auto-clears `CredentialId` and emits a `clear-credential` audit entry when a URL edit makes the existing credential host-incoherent; leaves `CredentialId` untouched when the new URL keeps the same host or is SSH. Add tests for the new `GET /api/repositories/credential-options?url=` mirroring the five existing by-ID tests (host match with masked tokens, `autoSelected` present for exactly one match, absent for zero and for multiple matches, 400 for missing/empty `url`).

### Frontend — API Client

8. **`gui/public/js/api.js`**: update `update(id, data)`'s JSDoc to document the now-optional `url` field alongside `name`. Add `credentialOptionsForUrl(url)`: `GET /api/repositories/credential-options?url=${encodeURIComponent(url)}`, then transform the raw `{credentials, autoSelected}` response into the flat `Array<{ credentialId, label, host, auto }>` shape the modal expects (an inline transform local to this new method — not shared with the existing, separately-flagged `credentialOptions(id)` method, so this fix does not alter that method's current behavior). Also normalize `updateCredential(id, credentialId)` — the shared wrapper both the new modal and the existing `repository-detail.js` credential dropdown call — so that `credentialId === ''` is converted to `null` before the request is sent, and correct its JSDoc (it currently says to pass `''` to clear; the server actually expects `null`, per `repositories.ts`'s `credentialId !== null` guard). Fixing this once at the wrapper, rather than at each modal call site, also repairs a live, currently-shipping bug in `repository-detail.js`'s credential-clear path — an unrelated call site that benefits automatically and is otherwise out of scope to touch. This normalization changes the request body sent for `updateCredential('repo-abc', '')`, which the existing real (non-mocked) test at `gui/public/js/api.config.test.mjs` (L440-448) currently asserts equals `{ credentialId: '' }`; update that assertion to `{ credentialId: null }` as part of this step (see also step 16).

### Frontend — New Modal Component

9. **Remove `buildAddRepoSection()`** and its collapsible-form DOM from `views/repositories.js`; replace with a single `<button class="btn btn-primary">+ Add Repository</button>` that calls `showRepositoryModal({ mode: 'create' })`, then on resolve calls `renderRepoTable(tableContainer)` again, and on rejection (cancel) does nothing.
10. **Remove the inline Name-edit machinery** from `buildRepoRow()` in `views/repositories.js` (the `nameInput`, `saveBtn`, `cancelEditBtn` elements and their listeners). The Edit button now calls `showRepositoryModal({ mode: 'edit', repo })`, then on resolve calls the row's refresh callback (rename the existing `onDeleted` parameter to `onChanged`, reused by both the Delete and Edit-save paths to trigger `renderRepoTable(tableContainer)`), and on rejection does nothing.
11. **Create `gui/public/js/components/modal-shell.js`** exporting `createModalShell({ titleText, ariaLabelledbyId, ariaDescribedbyId, className, onCancel }): { overlay: HTMLDivElement, modal: HTMLDivElement, mount(initialFocusEl?: HTMLElement): void, close(): void, setBusy(busy: boolean): void }`:
    - Build the `.modal-overlay` > `.modal` > `.modal-title` DOM exactly as `confirm-dialog.js` does today (`role="dialog"`, `aria-modal="true"`, `aria-labelledby`/`aria-describedby` set from the caller-supplied IDs — this amendment does not change these IDs from being literal per-component strings; randomizing them to support concurrent dialog instances remains the pre-existing, separately-accepted risk noted in `docs/agents/implementation-history/2026-04-03-phase6-gui-frontend/synthesis.md` and is not addressed here, see Out of Scope). Apply `className` (if provided) as an additional class on the `.modal` element, alongside the base `modal` class — this is how `repository-modal.js` (step 12) applies `.modal--form` without widening the shared rule.
    - `mount(initialFocusEl)`: capture `document.activeElement` into a closure-scoped `previouslyFocusedEl`; append `overlay` to `document.body`; attach a single `keydown` listener on `document` handling both Escape (invokes `onCancel()`, unless `setBusy(true)` is currently in effect, in which case it is a no-op) and Tab/Shift+Tab (the focus trap: query all focusable elements inside `modal` — `button, [href], input, select, textarea, [tabindex]:not([tabindex="-1"])` excluding `:disabled` — and on Tab from the last one, or Shift+Tab from the first one, call `event.preventDefault()` and explicitly `.focus()` the wrap-around element, since neither jsdom nor all browsers auto-advance focus at the trap boundary); attach a `click` listener on `overlay` that invokes `onCancel()` only when `event.target === overlay` (backdrop click) and `setBusy(true)` is not in effect; call `.focus()` on `initialFocusEl` if provided, else on the first focusable element inside `modal`.
    - `close()`: remove the `keydown` listener, remove `overlay` from its parent, and call `.focus()` on `previouslyFocusedEl` if it is still attached to the document (focus restoration).
    - `setBusy(busy)`: toggles a closure-scoped flag consulted by the Escape/backdrop-click handlers above; does not itself touch button `disabled` state — callers (`confirm-dialog.js`, `repository-modal.js`) remain responsible for disabling their own Confirm/Cancel/Submit buttons, since the shell has no knowledge of which buttons a caller built.

## Assumptions

- The "Add Repository" button's visual placement (currently a toggle button above a collapsible form) can become a simple modal-opening button without further layout changes to the Repositories page header.
- The new `.modal--form` modifier class (step 12, 560–600px max-width) accommodates the four-field form without further CSS beyond what step 12 specifies; the shared `.modal { max-width: 480px }` rule itself is left untouched, resolving the ambiguity the original version of this plan left open here.
- No project or workspace currently depends on `RepositoryManager.update()`'s signature being exactly `{ name: string }` (i.e., no other caller passes extra fields expecting them to be silently ignored, and no caller destructively relies on `url` being absent from the type) — confirmed by the fact `update()` is called from exactly one route handler in the codebase.

## Constraints

- Token masking for the new `GET /api/repositories/credential-options` endpoint must use the existing `'***'` convention (matching its by-ID sibling), not `config.ts`'s `maskToken()` convention.
- Every credential mutation (including the new auto-clear path) must emit a `Source: 'credential-audit'` audit-log entry, per `constraints.md`.
- All relative TypeScript imports must retain `.js` extensions (Node16 ESM).
- No plaintext token may appear in any new response, log message, or error string.
- The DOM/ARIA/Escape/backdrop-cancel/focus-trap/focus-restoration plumbing lives exclusively in `modal-shell.js` (step 11); neither `confirm-dialog.js` nor `repository-modal.js` may hand-roll a second copy of it — this is the structural decision this amendment makes and it must not be silently reversed during implementation.
- The focus trap's Tab/Shift+Tab handler must explicitly call `.focus()` on the wrap-around element at the first/last focusable boundary (neither jsdom nor all browsers auto-advance focus at a trap boundary); this is also what makes the trap directly unit-testable in `modal-shell.test.mjs` by dispatching a synthetic `keydown` and asserting `document.activeElement`.

## Out of Scope

- Repository ID rename (cascading updates to project `Repositories` references, on-disk clone-folder renames, `.code-workspace` regeneration) — explicitly deferred to a dedicated future plan per the Confirm-phase decision.
- Automatically re-pointing already-cloned repositories' local git remotes when the URL is edited (`git remote set-url` or re-clone) — the modal documents this as a caveat but does not perform it.
- Fixing the pre-existing `api.repositories.credentialOptions(id)` / `repository-detail.js` `buildCredentialSection()` bug (consumes the by-ID endpoint's real `{credentials, autoSelected}` shape as if already flattened) — flagged in Structural Improvements and Risks & Mitigations for a dedicated follow-up; not touched by this plan's new code paths.
- Backfilling `api-surface.md`'s pre-existing undocumented `api.repositories`/`api.projects`/`api.workspaces` method surface beyond the new/modified exports this plan introduces.
- Unifying the `'***'` vs. `maskToken()` token-masking-format inconsistency already flagged in `rest-api.md` as a known future cleanup item.
- Randomizing/parameterizing `confirm-dialog.js`'s and `repository-modal.js`'s hard-coded ARIA `id` values to support multiple concurrent dialog instances — flagged as a low-priority risk in the original `2026-04-03-phase6-gui-frontend` synthesis and left unaddressed here; `modal-shell.js`'s `ariaLabelledbyId`/`ariaDescribedbyId` parameters make the IDs caller-supplied rather than hard-coded *inside the shell*, but each caller still supplies its own literal, non-randomized string, so the underlying concurrent-dialog limitation is unchanged.

## Acceptance Criteria

- AC-01: The Repositories screen's "+ Add Repository" control opens a modal (not an inline collapsible form) containing URL, Name, ID, and Credential fields.
- AC-02: Submitting the create-mode modal with a valid URL creates the repository via `POST /api/repositories`, and if a credential was selected, associates it via `PUT /api/repositories/:id/credential` immediately, without a separate visit to the Repository Detail page.
- AC-03: Clicking "Edit" on an existing repository row opens the same modal in edit mode, pre-filled with the repository's current URL, Name, ID (disabled), and Credential.
- AC-04: Submitting the edit-mode modal updates the repository's Name and URL via `PUT /api/repositories/:id`, and updates the credential association via `PUT /api/repositories/:id/credential` only when the selection changed from its original value.
- AC-05: The repository ID field is disabled/read-only in edit mode and is never included in the edit submission payload.
- AC-06: Editing the URL to a host that no longer matches an already-assigned credential clears that association server-side and records a `clear-credential` audit-log entry.
- AC-07: Editing the URL to a duplicate of another repository's URL is rejected with a 400 error, surfaced in the modal (toast), and the modal remains open with the user's input intact.
- AC-08: In both create and edit modes, changing the URL field re-fetches and re-renders the credential dropdown's options against the new value, applying the established auto-select priority (stored/explicit value first, then a single unambiguous host match, else "None").
- AC-09: Cancelling the modal (Cancel button, Escape key, or backdrop click) in either mode makes no API calls and leaves existing data unchanged.
- AC-10: The inline per-row Name-edit toggle (input/Save/Cancel swapped in place of the name link) no longer exists in the Repositories table.
- AC-11: While either modal (`confirm-dialog.js` or `repository-modal.js`) is open, Tab and Shift+Tab cycle focus only among the modal's own focusable elements and never move focus to an element behind the overlay.
- AC-12: Closing either modal, by any dismissal path (Confirm/Cancel/Escape/backdrop-click for `confirm-dialog.js`; successful submit/Cancel/Escape/backdrop-click for `repository-modal.js`), restores keyboard focus to the element that had focus immediately before the modal opened.
- AC-13: On open, `confirm-dialog.js` continues to focus its Confirm button first (unchanged behavior); `repository-modal.js` focuses its URL field first, in both create and edit mode.
- AC-14: While a create/update call (and any follow-up credential-association call) is in flight in `repository-modal.js`, its Submit button, Cancel button, Escape key, and backdrop click are all disabled/no-op; all four are re-enabled if the call fails, and the modal stays open.

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| **Editing a repository's URL silently leaves already-cloned copies pointed at the old git remote**, producing confusing fetch/push behavior until manually corrected. | Documented as an explicit hint inside the edit-mode modal and in `rest-api.md`/`gui-frontend.md`; full auto-repointing is explicitly out of scope for this plan, not silently dropped. |
| **The pre-existing `credentialOptions(id)` bug** (Repository Detail page's credential dropdown never populates) remains unfixed after this plan ships, and could be mistaken for a regression introduced by this work. | Explicitly flagged in Structural Improvements and Out of Scope with the exact root cause and file/line evidence, so a future plan can address it without re-discovering it; this plan's own new code path is verified independent of the buggy method. |
| **Auto-clearing a credential on URL edit is a surprising side effect** if a user only intended to fix a typo in the URL's path (same host, e.g. a repo-name correction) that happens to also change something upstream unexpectedly. | The clear only fires when the *host* actually changes (not on path-only edits to the same host), and is paired with a visible audit-log entry and an immediate GUI dropdown refresh showing "None" so the user sees the state change rather than discovering it later. |
| **Duplicate-URL validation on edit could reject a no-op save** if a user resubmits the form without changing the URL (the "duplicate" would be the repository's own prior value). | The manager's duplicate check explicitly excludes the repository being updated (`r.Id !== id`) — this self-exclusion is new to `update()`, not mirrored from an equivalent `add()` pattern, since `add()` checks a brand-new record against the full store with nothing of its own to exclude. |
| **Refactoring `confirm-dialog.js` onto the new shell (step 11) could regress its existing, currently-shipping behavior**, since no dedicated test file exercises it directly today (only indirectly, and partially, via `settings.test.mjs`'s monkey-patch workarounds). | New `gui/public/js/components/confirm-dialog.test.mjs` (step 14) added specifically to cover `showConfirm()`'s resolve/reject contract, initial-focus, and focus-restoration behavior directly — this plan is the first to give `confirm-dialog.js` its own regression suite, precisely because this plan is the one changing its internals. |

## Recommended Workflow

- **Workflow:** ledger
- **Rationale:** The plan spans multiple modules (backend model, backend routes, GUI API client, GUI view, two new GUI components, and a refactored existing component) with 20 detailed steps across distinct concerns (data-integrity validation, a new endpoint, a new shared accessibility primitive, a new reusable UI component, and coordinated test/documentation updates), and benefits from the formal QA, security-audit, and review stages given the credential-handling, data-mutation, and accessibility surface involved.
